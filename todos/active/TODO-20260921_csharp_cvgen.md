## Objective

Port cpp `cvgen` (`pwiz/data/common/cvgen.cpp` + `cvgen_common.hpp` + the parts of `obo.cpp`
that shape identifiers) to C# so the .NET port can regenerate `CVID.generated.cs` from the OBO
files without a C++ build. Until now `pwiz-sharp/pwiz/src/Common/generate_cvid.py` copied the
enum body out of the cpp-generated `cv.hpp` — the last cpp dependency of a CV refresh, and one
that disappears entirely when #4658 retires the C++ tree. Requested by Matt after #4339 could
not take psi-ms 4.2.2 for exactly that reason.

## What was done

- `pwiz-sharp/build/CvGen/` — console tool (`dotnet run --project pwiz-sharp/build/CvGen`) +
  `CvidEnumGenerator` (public, referenced by Common.Tests). Only the enum half of cvgen is
  ported: the term tables `cv.cpp` held are read from the embedded OBOs at run time by
  `CvLookup`. Defaults: the three OBOs under `<repo>/pwiz/data/common/`, output
  `pwiz-sharp/pwiz/src/Common/CVID.generated.cs`, repo root found by walking up from the exe.
- `OboParser` brought to cpp `obo.cpp` parity where it shapes identifiers:
  - term ids with letters (NCIT:C25330) read as A..Z -> 1..26 (325330), instead of skipping
    the stanza; NCIT terms were always in the enum (`NCIT_Duration = 100325330`)
  - `def:` parsed with cpp's regex: the `OBSOLETE ` prefix is stripped and sets IsObsolete
    (assignment, as cpp), escaped `\"` inside the text survive, an NCIT `{...="NCI"}` tail no
    longer swallows the definition
  - `comment:` stands in for a missing `def:`
  - `synonym:` parsed with cpp's regex (scope word must be `EXACT`); `exact_synonym:` accepted;
    cpp `add_synonym`'s hex encoding of a synonym that differs from the name only in
    punctuation (`LTQ Velos ETD` -> `LTQ Velos_x20_ETD`), byte-wise on UTF-8
  - `ObOntology.Terms` is now a file-ordered `List<OboTerm>` with `FindTerm(prefix, id)`:
    the old `SortedDictionary<uint, OboTerm>` keyed on the number alone, so psi-ms.obo's
    PEFF:0000001.. were overwritten by its UO:0000001.. copies and MS:1002001-3 by
    PEFF:1002001-3 (their `CvTermInfo` fell back to enum-derived names at run time)
- `CVID.generated.cs` regenerated by the tool. Parity with the cpp-generated file (6451
  members incl. NCIT letter ids, `_xNN_` / `__micro__` escapes, `_OBSOLETE`, value-suffixed
  collisions like `MS_M_H_ion_1002820`, synonym aliases + the MS_TOF_TOF dedup) is exact
  except for **three additions**: `PEFF_regular_expression_for_...` 201002001-201002003,
  which cvgen dropped because its `std::set<Term>` was keyed on the number alone and
  MS:1002001-1002003 got there first. Their values do not collide, so they are kept; the
  generator comment records this as the one deliberate difference.
- Tests (`Common.Tests/CvidEnumGeneratorTests`): (1) the checked-in `CVID.generated.cs` equals
  what the generator produces from the tracked OBOs — an OBO refresh cannot land without its
  regenerated enum; (2) one inline OBO pair exercising every identifier rule.
  `OboParserTests` extended for the escape handling. Common.Tests now references
  `TestHarness` (PwizSharpPaths) and `build/CvGen`.
- Removed `generate_cvid.py`; updated `pwiz/src/Util/README.md`, `docs/module_detail.py` and
  the derived `module-detail-data_common.{dot,svg}` tooltips.

## Review findings addressed (2026-09-22)

A `/code-review max` pass ran against this tree (`cvgen-review.md`, 15 findings). Each was
verified against the cpp sources and the shipped OBOs before acting; the counts below are
measured, not quoted.

**Real bugs, fixed:**
- **xsd: value-type relationships (finding 1).** `TryParseId` gained letter translation for
  NCIT accessions, and `ParseRelationship` shares it, so `relationship: has_value_type
  xsd:float` began parsing as term 61215120. Measured: of psi-ms.obo's 1366 such lines, 1155
  became fabricated `RelationEntry` records and 211 were dropped, sorted only by which
  spellings overflow `uint`. cpp guards with `istarts_with(relation, "xsd:")`; so do we now.
  Inert today only because `CVTermInfo.OtherRelations` is not yet populated from
  `OboTerm.Relations` - the reviewer was right that wiring that up would have made it live.
- **Cross-prefix `is_a` (finding 5).** A parent id is stored bare and re-homed into the
  CHILD's block, so psi-ms.obo's 9 cross-prefix lines invented relations: the five
  `is_a: UO:0000000 ! unit` terms (MS:1000040/43/46, MS:1000807, MS:1002814) each got
  `(CVID)0`, the MS root, making `CvIsA` answer true where cpp answers false. cpp
  `parse_is_a` rejects them; now so do we. Pre-existing for numeric targets, newly reachable
  for letter ones.
- **`AddSynonym` mixed-byte decode (finding 9).** Interleaving raw UTF-8 bytes with ASCII
  `_xNN_` markers and decoding the result as UTF-8 yields U+FFFD whenever the difference falls
  inside a multi-byte sequence. Now compares and substitutes per CHARACTER, which is identical
  to cpp's per-byte behaviour for the ASCII punctuation every real case involves and cannot
  emit a lone continuation byte. Zero occurrences in the shipped OBOs; this was armed for the
  next refresh.
- **Header bound and namespace capture (finding 6).** The header now ends at the first BLANK
  line (cpp `parse()`), not the first stanza - unimod.obo differed by two lines - and the
  namespace remark is captured with cpp's `(\w+)`, so `remark: namespace: PSI-MS` would
  declare `PSI`, not `PSI-MS`. Both feed the prefix set that numbers the value blocks, where a
  disagreement shifts every later block by 100,000,000.
- **Style (finding 15).** Single-line `if` in `TranslateLetters`; em dashes on the lines this
  change adds (the file has 88 pre-existing ones, left alone); the stale
  `PORT_STATUS["data/common/cvgen"]` comment still crediting the python generator.

**Guards added rather than silent failure:**
- `Generate` refuses an `ObOntology` with no `Filename` (finding 2): the rule that drops
  psi-ms.obo's 53 duplicated UO terms is keyed on it, exactly as cpp's `parseStanza` is, so a
  stream-parsed ontology would have renumbered the blocks AND emitted 53 duplicate
  identifiers.
- `Generate` throws on a duplicate enumerator (finding 10) instead of emitting source that
  cannot compile. cvgen let its own build catch this; here the artifact is committed, so the
  failure would have surfaced as CS0102 in `CVID.generated.cs` with the policing test green.
- `GeneratedValues_AgreeWithCvLookupOffsets` (finding 3): the prefix->block numbering has two
  owners (the generator derives it, `CvLookup` hardcodes `Offset*`) and nothing tied them
  together. A new namespace sorting before an existing one would renumber, the staleness test
  would say "regenerate", and every PEFF/UNIMOD/UO accession would then be computed against
  the wrong offset with nothing failing first.
- `CvidGeneratedCs_MatchesCppCvHpp` (finding 4): parses identifier=value out of cpp's
  `cv.hpp` and asserts the C# enum is a superset with matching values - restoring the cpp
  parity check that deleting `generate_cvid.py` removed. Goes Inconclusive when the cpp tree
  is retired.
- Tests for the two runtime data changes the review flagged as uncovered (finding 11), plus
  the xsd and cross-prefix guards, in `OboParserTests`.

**Reduced blast radius:**
- `Common.Tests` no longer takes a `TestHarness` ProjectReference (finding 13); it
  source-links the self-contained `PwizSharpPaths.cs`. Measured: the test output went
  39 MB -> 15 MB and no longer carries HDF5 natives, `MassLynxRaw.dll`, Analysis, MsData or
  TestHarness, nor gates a clean build on the encrypted Waters archive.
- `PwizSharpPaths` use in the new tests is wrapped to `Assert.Inconclusive`, matching
  `CodeInspectionTests` and `Installer.Tests` (finding 12).
- CvGen resolves the repo root only when a default needs it, validates its arguments, requires
  `--output` when OBO files are named explicitly (a partial list used to overwrite the tracked
  `CVID.generated.cs` and exit 0), and creates the output directory (findings 7, 8).

**Assessed and deliberately NOT changed:**
- **Finding 14 (duplicated escaping logic).** `NormalizeForComparison` and
  `ToEscapedCharacters` do differ - and they differ in cpp too, for the same reason: they are
  cpp's two distinct rules (`add_synonym`'s `isalnum` normalization vs `toEscapedCharacters`,
  which keeps `_` and honours the named UTF-8 table). Unifying them would diverge from cvgen
  rather than fix anything. Documented in place instead.
- **Finding 11's framing.** Both behaviour changes are corrections TOWARD cpp, not
  regressions: `cv.cpp` records MS:1001152 as `isObsolete = true` and `cv.hpp` names it
  `MS_param__y_ion_H2O_DEPRECATED_OBSOLETE`, so the previous C# parser disagreed with the very
  enum it was generated from. Same for the 15 terms the id-keyed dictionary evicted. Now
  covered by tests.
- **NCIT has no `CvLookup.Offset` constant**, so its 16 CVIDs resolve to `"??:0000000"`.
  Pre-existing (NCIT was already in the enum via cv.hpp), no mzML impact, not this change's
  business. Recorded under Follow-ups.
