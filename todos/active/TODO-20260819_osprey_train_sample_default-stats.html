Two earlier drafts are excluded from this analysis. pickrun and pickrun2 each carried a defect and neither shipped; pickrun2 drew over rows rather than runs, which weighted each run by how many candidate peaks it produced and left a random candidate as the training row. They mattered historically — the row-vs-run distinction is what led to pickrun3 — but as arms they only add noise, so their numbers appear here only where they are the sole evidence for something (section 3).
Why it matters: the maximum makes every training row an extreme value over however many files were batched together, while the model then scores ordinary per-run rows. Mean coelution_sum is 1.19 at one file and 5.75 at 82, against 1.18 in the population being scored — so the distortion grows with batch size, and so does the benefit of removing it.

2How to read these tables

Pass 1 vs pass 2 — use the toggle

Pass 1 is the training change's own scope. Pass 2 re-scores against a frozen model with protein-compact stratified competition, and the .blib is written from pass 2. A count taken off the blib is therefore not comparable to a pass-1 table — that mismatch produced one wrong figure in this investigation, corrected in section 4.

Nominal q vs matched true FDP

n@1% q is the count at the reported 1% q cutoff — what a user actually gets. FDP at that q is what that cutoff really cost, measured against entrapment. The @0.650% / @0.750% / @1.000% columns re-cut both arms at the same true error, which is the only fair comparison: an arm can always report more identifications by spending more error.

Only entrapment datasets can do this. Plain Stellar and the stock Astral regression spec carry no entrapment, so they have no true-FDP oracle and can only produce raw counts (section 5).

Both libraries now gain the same from pass 2: +15.2% for ours (45,943 → 52,911) against +15.1% for Mike's (41,563 → 47,855). The asymmetry that drove this investigation — Mike +22.7% against our +12.5% — was a property of the superseded peak-level sampler, not of the libraries. The samplers swap the libraries' pass-2 outcomes outright: ours 48,353 → 52,911 (+9.4%), Mike's 52,381 → 47,855 (−8.6%), the same directions as their pass-1 movement (+33.0% / −3.3%) and larger.

The pass-2 lever delta, completed 2026-08-20: our library 35,327 → 52,911, +49.8%, against Mike's 42,679 → 47,855, +12.1%. The sampler's advantage on our library is larger at pass 2 than at pass 1 (+49.8% against +33.0%) while Mike's shrinks (+12.1% against +15.0%). This is what the earlier +22.7%-for-Mike figure obscured: it was the only pass-2 lever delta that existed, and it was measured on the superseded sampler.

One arm barely gains from pass 2 at all. Pass 1 → pass 2 is +15.2% (ours pickrun3), +15.1% (mike pickrun3) and +18.1% (mike baseline) — but only +2.2% for ours baseline (34,552 → 35,327). Under the cross-run maximum our library's first-pass model is poor enough that the second pass recovers little from it, so the damage compounds rather than washing out downstream. That is the mechanism behind the +49.8%.

All three arms logged the protein stratum line; the baseline arm additionally logged [TRAIN] OSPREY_TRAIN_PICK_RUN=0, confirming the sampler was in force rather than merely intended; and every arm reproduces its pass-1 count to the digit against an independent earlier run. Pass-2 FDP is inflated in every arm (1.05–1.78% against pass 1's ~0.85%), the known second-pass recalibration issue, which is why matched-FDP is the comparator here rather than the count at nominal q.

7What is not measured

  • Wall clock from these arms is not a performance measurement. The baseline pass-2 arm ran 8–11% slower per stage than the two pickrun3 arms while re-scoring 25% fewer entries (5.06 M against 6.73 M), so the extra time is not extra work. Another session was running /code-review max and building in a second checkout across that window — the same CPU-contention confound already recorded for the 2026-08-19 Mike arm.
  • Astral 3-file pass 2. Both Astral arms were run as -Task FirstPassFDR, so they have no pass-2 stage.
  • Replication — answered, not outstanding. These runs are deterministic: PercolatorConfig.Seed is a fixed 42, and the reservoir is keyed by a SplitMix64 mix of (base_id, k, seed) so thread scheduling cannot move it. The three 2026-08-20 arms reproduced 45,943 / 41,563 / 34,552 exactly against independent earlier runs, and regression.ps1 gates byte-identical output against a committed golden on every commit. Re-running an identical config returns an identical number.
  • v2 vs v3 library, isolated. The two Stellar libdecoy goldens confound the training change with the v2→v3 library swap. Now cheap to run: the additive extraction means a swapped-in library survives.
  • Second-pass training. The selection is read from a process-wide static with no pass parameter, so it also governs second-pass and per-file-rescore training, where gap-fill rows are target-only and resolve to synthetic zero-feature vectors. Under the maximum those rows essentially never won a slot; under a reservoir each wins with probability 1/k. A plausible contributor to the opposite-direction pass-2 movement in section 4.
  • C#/Rust parity. This default is C#-only; Rust still takes the cross-run maximum, so the two agree only under OSPREY_TRAIN_PICK_RUN=0.
